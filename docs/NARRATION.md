# 책 나레이션 사전 제작 · RunPod Qwen3-TTS

## 구현 범위

`prompt` 프로젝트의 `src/lib/server/tts/qwen-runpod.ts`, `runpod.ts`, `runpod-workflows/qwen3-tts-worker/handler.py`에서 확인한 Qwen3-TTS CustomVoice 계약을 재사용한다. 기본은 **Qwen3-TTS-12Hz-1.7B-CustomVoice / Sohee / Korean**이다. 원본 prompt 프로젝트 코드는 수정하지 않았다.

API 키는 prompt의 `.env.local`에서 현재 프로젝트의 `.env.local`로만 복사했다. 실제 값은 로그·문서·브라우저 코드에 포함하지 않는다. 다른 공급자용 `NARRATION_API_KEY` 자리는 그대로 남겨 둔다. 공급자 자동 fallback은 없다.

현재 웹 어드민은 원고 묶음을 만들고 완성 결과를 가져오는 로컬 운영 UI다. **유료 생성은 로컬 운영자의 CLI에서만** 실행할 수 있다. 공개 HTTP 생성 API는 계속 503으로 차단된다. 실제 클라우드 관리자/제작자 권한, 서버 큐, Firebase 음원 배포는 아직 연결하지 않았다. 따라서 브라우저의 역할 표시나 버튼을 바꿔도 RunPod를 호출할 수 없다.

## 현재 엔드포인트 확인 결과

2026-11-04에 RunPod 관리 API의 GET으로만 조회했다. 워커를 켜거나 생성 요청을 보내지 않았다.

- ID: `5vsbugwjlp0hnz`
- 이름: `playlab-qwen3-tts-17b-v2`
- 최소 워커 0, 최대 워커 1, GPU 수 1, idle timeout 5초
- 작업 실행 제한 600초
- 연결된 network volume 없음
- 16GB·24GB·48GB GPU 여러 종류가 허용됨. 실제 배정 종류는 작업/워커 이력으로 확인해야 함.

이 엔드포인트는 prompt와 공유한다. 기존 설정을 변경하거나 전체 큐를 비우지 않는다. 이 도구가 제출하고 ID를 보관한 작업에 대해서만 취소 요청을 보낸다. prompt의 앱 내부 운영 허용 설정까지 공유해서 읽지는 않으므로 운영자가 다른 앱과의 동시 사용·중지 의도를 조율해야 한다. 실행 전 확인을 위해 `npm run narration:inspect`로 읽기 전용 설정 조회가 가능하다.

## 시간당 원가 기준

2026-11-04 확인한 [RunPod 공개 Serverless 요금표](https://www.runpod.io/pricing) 기준, GPU 1개:

| 허용 GPU 종류 | USD / GPU 시간 |
| --- | ---: |
| A4000 / A4500 / RTX 4000 Ada / RTX 2000 Ada | $0.58 |
| A5000 / L4 | $0.75 |
| A40 / A6000 | $1.22 |
| RTX 4090 | $1.34 |

따라서 현재 구성은 **시간당 $0.58~$1.34의 계산비**로 예산을 산정한다. 실행 10분이라면 계산비만 약 **$0.0967~$0.2233**다. 이 숫자는 책 한 권의 실제 제작 시간을 의미하지 않는다. 책의 길이, 발음·속도, GPU 배정, 모델 로딩에 따라 시간이 달라지므로 실제 책으로 측정해야 한다.

[공식 과금 안내](https://docs.runpod.io/serverless/pricing)에 따르면 워커 시작부터 완전 정지까지 초 단위로 과금하며 모델 준비, 실행, 마지막 idle 대기 등이 포함된다. 컨테이너 디스크는 별도 과금 대상이다. 계정 크레딧·자동 충전·세금·계약 할인은 확인하지 않았으며, 무료 사용량이나 무과금을 가정하지 않는다. 새 구독·자동 충전·상시 워커·저장소는 설정하지 않았다. `workersMin=0`이라도 이미 실행 중인 워커나 남아 있는 저장 비용까지 무료라는 뜻은 아니다.

현재 보고서는 **실행 시간 기준 추정치**와 **예산 예약액**을 구분한다. 작업 `executionTime`은 전체 청구 가능한 워커 수명과 같지 않다. 최종 원가는 RunPod 실제 사용 내역과 대조해야 한다. 로딩·idle·디스크·세금은 보고서 추정액에 포함되지 않는다. 같은 워커를 다른 앱과 공유하므로 다른 앱 사용량도 이 보고서에 섞어 넣지 않는다.

## 제작 흐름

1. 어드민 → AI 제작 대기열 → 책 나레이션 일괄 제작에서 여러 책, 목소리, 언어, 구간 길이를 선택한다.
2. **원고 묶음 내려받기**를 누른다. TXT는 리더와 같은 페이지, PDF는 페이지 텍스트를 추출한다. 텍스트 없는 PDF 페이지가 있으면 누락해서 진행하지 않고 OCR/빈 페이지 검수를 요구한다. 이미지 원고와 가이드 데모는 제외한다.
3. 내려받은 JSON으로 오프라인 계획을 준비한다:

```powershell
npm run narration:prepare -- "C:\path\folio-narration-manuscripts.json"
```

`data/narration/<batchId>/`에 plan.json, journal.json, approval.example.json을 만든다. 기존 진행 기록은 덮어쓰지 않는다. 책 본문·음성 설정의 해시가 같으면 같은 batchId를 사용한다. 이 단계는 RunPod 호출이 없다.

4. **실행 전에** 사용자에게 대상 책, 공급자, 단가, 예상 비용/불확실성, 최대 요청 수, 예산, 승인 기한, 별도 디스크 비용과 자동 충전 상태를 설명하고 명시적 승인을 받는다. 승인 없이는 아래 단계에 들어가지 않는다.
5. 승인 범위만 `approval.json`으로 작성한다. `approval.example.json`은 승인 자체가 아니다. `approvedBy`, 정확한 fingerprint/endpoint, expiresAt, maxReservedUsd, maxSubmissions, 시간당 상한, 실행 제한, 로딩 예상치를 기록한다. `acknowledgeUnmeteredOverhead`는 실제 비용이 예약액과 다를 수 있음을 승인 범위에 포함했다는 운영 기록이다.
6. 승인 후에만 `.env.local`의 `NARRATION_ENABLED=true`로 바꾸고 실행한다:

```powershell
npm run narration:run -- <batchId>
```

구간별 `/run` → `/status`로 순차 실행한다. 각 POST 전에 디스크에 상태와 예산 예약을 먼저 기록한다. 승인 기한·요청 수·예약 상한 및 공유 엔드포인트 상태를 다시 검사한다. GPU/최소·최대 워커/idle/볼륨 설정이 허용 범위 밖이면 수정하지 않고 중단한다.

7. 구간 WAV, journal.json, report.json, report.csv, narration-result.json을 같은 폴더에 저장한다. **완료한 책만** narration-result.json에 들어간다. WAV의 실제 byte rate/data size로 음원 길이를 측정한다. 응답의 실행 시간, 큐 대기 시간, 관측 시간도 따로 보존한다.
8. 어드민에서 **완성 음원 폴더 가져오기**로 폴더를 선택한다. 원본 해시와 구간 위치를 검증하고 음원을 브라우저에 저장한다. 해당 책의 듣기 버튼은 생성된 음원을 우선 재생한다. **제작 리포트 가져오기**로 report.json을 열어 책별 시간을 비교한다.

현재 기존 워커는 문장별 타임코드를 반환하지 않는다. 따라서 재생 시 페이지를 이동하고 텍스트 패널에서 **제작 구간 단위**로 강조한다. 단어·문장에 정확히 맞는 타임코드라고 표시하지 않는다. 정밀 동기화는 후속 정렬 단계가 필요하다.

## 중단, 재개, 오류

- Ctrl+C는 다음 제출을 막고 체크포인트를 남긴다. 이미 제출된 작업은 계속 실행될 수 있다.
- `npm run narration:cancel -- <batchId>`는 알려진 진행 작업 ID에만 취소를 요청한다. 취소 요청은 즉시 과금 종료를 보장하지 않는다. 다시 상태를 조회해 종료를 확인한다.
- 같은 `narration:run` 명령으로 기존 작업을 조회하고 이어간다. 승인 만료 시 이미 제출한 결과 수집은 가능하지만 새 제출은 막는다. 환경변수 활성화와 승인 범위 일치는 여전히 필요하다.
- POST가 네트워크 오류로 끝나면 실제 제출 성공 여부가 불명확하므로 **자동 재제출하지 않는다**. RunPod 콘솔에서 확인해 작업 ID를 journal에 연결하거나 오류를 수동 정리해야 한다.
- 실패한 작업도 자동 재시도하지 않는다. 추가 생성 비용을 승인받은 후 새 계획/명시적인 재처리가 필요하다.
- 동시 CLI 실행은 batch.lock으로 막는다. 비정상 종료로 잠금이 남으면 기존 프로세스와 RunPod 작업 상태를 확인한 뒤 운영자가 잠금을 제거한다.
- 보고서만 갱신: `npm run narration:report -- <batchId>` (네트워크 없음).
- 예산 예약은 `(실행 제한 + 로딩 예상 + idle) × 단가 상한`을 보수적으로 누적한다. **클라우드 하드 지출 상한이 아니다.** 실제 로딩 시간·디스크·세금이 다를 수 있고, 다른 앱의 사용을 제어하지 못한다. 계정 전체 비용 통제는 별도로 검토해야 한다.
- 장시간 Vercel 요청에 제작을 붙이지 않고 로컬 프로세스로 진행한다. 실행 중 컴퓨터를 끄지 않는다. 완료 결과의 RunPod 보존 시간은 제한적이므로 바로 로컬에 보관한다.

## 확인한 것과 남은 것

오프라인 단위 테스트로 분할/원문 보존, 승인 차단, 예산 차단, 엔드포인트 변경 차단, 중복 방지, 재개, 오류 결과, WAV 길이, 공급자 계약을 검사했다. 두 권짜리 테스트 원고의 계획 생성도 오프라인으로 확인했다. 실제 유료 생성, 실측 책당 제작 시간, 브라우저 폴더 가져오기/재생 전체 흐름은 아직 검증하지 않았다. RunPod 과금 작업과 Firebase 업로드 및 Vercel 변경은 실행하지 않았다.
